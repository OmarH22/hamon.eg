# HAMON — Market Validation Landing Page

A short, RTL Arabic landing page that presents the HAMON height-increasing sneaker concept
and collects **anonymous** research answers, plus a private dashboard for reading the results.

It is not a shop, a preorder page or a waitlist. It asks one question: **is there real
purchase interest in this product in the Egyptian market?**

- No name, email, phone, WhatsApp, address or account is ever requested.
- No pricing question in this version (the architecture is ready for one — see below).
- No fabricated reviews, counts, dates, claims or scarcity anywhere on the page.

## 2. Supabase setup

1. Create a project at <https://supabase.com>.
2. Open **SQL Editor**, paste the contents of `supabase/migrations/0001_init.sql`, and run it.
   It creates two tables, their constraints and indexes, then locks both down.
3. Go to **Project Settings → API** and copy:
   - **Project URL** → `SUPABASE_URL`
   - **service_role** key → `SUPABASE_SERVICE_ROLE_KEY`

That is the whole setup. Two tables are created:

- `survey_submissions` — one row per completed questionnaire.
- `survey_events` — anonymous funnel events (`page_view`, `product_view`, `form_start`,
  `form_submit`), one row per session per type.

### Why there is no public Supabase key

The browser never talks to Supabase. Every write goes through this app's own API routes, which
use the service-role key **server-side only**. That is why the schema enables Row Level Security
with **no policies at all** and revokes the `anon` / `authenticated` grants: even if someone
found a Supabase key, those roles can neither read nor write these tables.

## 3. Environment variables

Copy `.env.example` → `.env.local`. Nothing in the repository contains a real secret.

### Server-only — never exposed to the browser

| Variable | Purpose |
| --- | --- |
| `SUPABASE_URL` | Supabase project URL. |
| `SUPABASE_SERVICE_ROLE_KEY` | Service-role key. Full database access — server only. |
| `ADMIN_PASSWORD` | Password for `/admin`. Minimum 8 characters. |
| `ADMIN_SESSION_SECRET` | Signs the admin session cookie. Minimum 16 characters. |

Generate a session secret:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

### Public — bundled into the browser, nothing secret

| Variable | Purpose |
| --- | --- |
| `NEXT_PUBLIC_META_PIXEL_ID` | Meta Pixel ID. Leave empty and no pixel script loads at all. |
| `NEXT_PUBLIC_SITE_URL` | Canonical URL for metadata, Open Graph, `robots.txt`, sitemap. Optional on Render — falls back to `RENDER_EXTERNAL_URL`. |
| `NEXT_PUBLIC_LANDING_VARIANT` | Optional label stored with every response (default `v1`). |

If `ADMIN_PASSWORD` or `ADMIN_SESSION_SECRET` is missing or too short, admin login fails
closed — no session can be issued and `/admin` stays inaccessible.

## 4. Deploying to GitHub + Render

### 4.1 Push to GitHub

The repository is already initialised and committed. Create an **empty** repo on GitHub (no
README, no .gitignore), then:

```bash
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPO.git
git push -u origin main
```

Nothing secret is in the repository: `.env.local` is git-ignored and `.env.example` contains
only blank placeholders.

### 4.2 Deploy on Render

`render.yaml` at the repo root is a Render Blueprint — it defines the service, so you do not
configure anything by hand.

1. In Render: **New → Blueprint**, connect GitHub, pick the repository.
2. Render reads `render.yaml` and asks for the values marked `sync: false`:
   - `SUPABASE_URL`
   - `SUPABASE_SERVICE_ROLE_KEY`
   - `ADMIN_PASSWORD`
   - `NEXT_PUBLIC_SITE_URL` — leave blank on the first deploy
   - `NEXT_PUBLIC_META_PIXEL_ID` — leave blank to run without the pixel

   `ADMIN_SESSION_SECRET` is generated by Render automatically and kept across deploys.
3. **Apply**. The first build takes a few minutes.
4. Once live, set `NEXT_PUBLIC_SITE_URL` to your Render URL (e.g.
   `https://hamon-validation.onrender.com`) or your custom domain, and redeploy. Until you do,
   the app falls back to Render's own `RENDER_EXTERNAL_URL`, so `robots.txt` and the sitemap are
   already correct — only the Open Graph image URL needs the explicit value baked in at build.
5. Open `/admin`, sign in with `ADMIN_PASSWORD`, and confirm the dashboard loads.

### What the blueprint sets, and why

| Setting | Value | Reason |
| --- | --- | --- |
| `region` | `frankfurt` | Render's closest region to Egypt. |
| `plan` | `free` | Costs nothing, but spins down after 15 minutes idle: the first visitor after a quiet period waits ~50s. Change this one line to `starter` ($7/mo) before running paid ads, or the cold start will be measured as lost interest. |
| `buildCommand` | `npm ci --include=dev && npm run verify:copy && npm run build` | Render sets `NODE_ENV=production`, so `--include=dev` is required or TypeScript/Tailwind are missing at build time. `verify:copy` fails the deploy if the locked Arabic copy was altered. |
| `startCommand` | `npm start` | `next start` binds `0.0.0.0` and reads Render's `PORT` automatically. |
| `healthCheckPath` | `/api/health` | Liveness only — it never touches Supabase, so a database hiccup cannot cause Render to cycle a healthy service. |
| `.node-version` | `22` | Pins the Node major on Render and for local `nvm`/`fnm` users. Put a full version here (`22.20.0`) to pin exactly. |

Deploys are automatic on every push to `main` (`autoDeploy: true`).

### Custom domain

Add it under **Settings → Custom Domains**, point the DNS record at Render, then update
`NEXT_PUBLIC_SITE_URL` and redeploy. Render provisions the TLS certificate.

### Production headers

Set for every response in `next.config.mjs`, enforced only in production builds:
Content-Security-Policy, Strict-Transport-Security, `X-Frame-Options: DENY`, `nosniff`,
Referrer-Policy and Permissions-Policy. `/admin` and `/api` additionally send `no-store`.

The CSP allows inline scripts (`'unsafe-inline'`) because Next.js inlines its hydration
bootstrap and the Meta Pixel snippet without a nonce — it still blocks scripts from any host
that is not explicitly listed, which is the attack that matters here. If you add a third-party
script later, add its origin to `script-src` and `connect-src` or it will be blocked.

The admin session cookie is `httpOnly`, `sameSite=lax` and `secure` in production, so the site
must be served over HTTPS — Render does this by default.

### Other hosts

Any Node host works: build with `npm ci --include=dev && npm run build`, serve with `npm start`,
and provide the same environment variables. There is no platform-specific code — `render.yaml`
and `.node-version` are the only Render-specific files.

## 5. Admin dashboard

`/admin` — password login, 12-hour signed session, `noindex` at three levels (middleware header,
route metadata, `robots.txt`).

It shows:

- **Overview** — total responses, responses today, sessions, product views, form starts,
  confirmed submissions, form-start rate, submission rate, session→submission rate.
- **Breakdowns** — purchase intent, shoe size (ordered as a size curve), colour, most important
  factor, main barrier. Counts and percentages with bars.
- **Other barriers** — the free text typed after choosing *سبب تاني*.
- **Open feedback** — every open answer with its timestamp and purchase-intent level.
- **Acquisition** — UTM source / medium / campaign / content. Responses that arrived without
  UTM parameters are shown as `(not set)`; nothing is invented.
- **Export CSV** — every response with timestamps (Cairo and UTC), the anonymous session id,
  each answer as both internal value and Arabic label, the free-text fields and the full
  attribution. No secrets or authentication data are ever exported.

## 6. Brand and product images

**Every image reference in the site lives in one file: `src/lib/assets.ts`.**
No component needs editing to swap artwork.

| What | File | Notes |
| --- | --- | --- |
| HAMON logo | `public/brand/hamon-logo.png` | 927×180, transparent background, tinted to the brand ink |
| Hero | `public/products/hamon-hero.jpg` | 1600×1600, white sneaker with extra margin for the 5:4 desktop crop |
| White sneaker | `public/products/hamon-white.jpg` | 1600×1600 |
| Black sneaker | `public/products/hamon-black.jpg` | 1600×1600 |
| Favicon | `public/brand/favicon.png` | 512×512, the logo's H in ivory on ink |
| Social share | `public/brand/hamon-og.jpg` | 1200×630, wordmark + product on white |

These were generated from the supplied artwork. Three things were done to it:

- **The "White" / "Black" captions were cropped off** the bottom of both product
  photos — they were burned into the source images and would have shown on the page.
- **Both shoes were scaled by one common factor** and centred on identical square
  canvases, so the two cards read as a matched pair rather than two loose photos.
- **The logo's white background was made transparent.** The source was a JPEG on
  solid white, which would have appeared as a white box on the ivory header.
  Alpha is derived from the artwork's luminance, so anti-aliased edges survive.

### Replacing them later

1. Drop the new file into the same folder.
2. Point `src/lib/assets.ts` at it.

Raster files (`.jpg`, `.png`, `.webp`) go through the Next.js image optimizer, which
generates responsive AVIF/WebP variants — the hero currently ships as 4 KB at 384px
wide and 12 KB at typical phone width, from a 36 KB source.

**Shoot square, product centred, roughly 10% breathing room.** The hero crops to 5:4
on wide desktops; every other slot is exactly square, so nothing is ever distorted.
Keep the social share image at exactly 1200×630, and use JPG or PNG for it — SVG does
not render on social platforms.

If you swap the hero for the black sneaker, change its `alt` to `ALT.black` in the
same file.

## 7. Changing survey questions and options

**`src/lib/survey.ts` is the single definition of the questionnaire.** The form UI, client
validation, server validation, the CSV export and every dashboard breakdown are derived from it.

To add an option:

```ts
{ value: 'internal_value', label: 'النص العربي اللي هيتعرض' },
```

- `value` is stored in the database and never shown.
- `label` is what the visitor reads.

Then **add the new value to the matching `CHECK` constraint** in a new SQL migration, or the
database will reject responses using it:

```sql
alter table public.survey_submissions
  drop constraint survey_submissions_shoe_size_check,
  add constraint survey_submissions_shoe_size_check
    check (shoe_size in ('38','39','40','41','42','43','44','under_38','over_44','45'));
```

Other levers on each question:

| Field | Effect |
| --- | --- |
| `layout` | `'list'` stacked radio cards · `'chips'` compact pills · `'color'` image cards |
| `enabled` | `false` removes the question from the form **and** from validation |
| `followUp` | Reveals a text field when a specific option is chosen (used by *سبب تاني*) |
| `reportOrder` | Dashboard ordering when it should differ from the form order |
| `maxLength` | Character cap on text answers |

Reordering the array reorders the form; the `01…06` markers renumber themselves.

### Adding the pricing question later

Everything is already in place:

1. The column `price_expectation` exists in `survey_submissions`, nullable and unconstrained.
2. A commented-out question block sits at the bottom of `SURVEY_QUESTIONS` in
   `src/lib/survey.ts`.

To ship it: uncomment the block, replace the `TODO` strings with your approved Arabic copy, and
optionally add a `CHECK` constraint once the price bands are final. The form, validation, CSV
export and a new dashboard panel all pick it up automatically — add an English title for the
panel in `PANEL_TITLES` in `src/app/admin/page.tsx`.

## 8. Copy rules

**All customer-facing Arabic text lives in `src/lib/copy.ts` and `src/lib/survey.ts`, and is
locked.** Components render those strings verbatim — no component contains a hard-coded Arabic
sentence. Every locked string was verified character-for-character against the approved source.

```bash
npm run verify:copy
```

That guard asserts two things and fails the command if either breaks: every approved string
still appears character-for-character, and no Arabic literal has crept into any other file.
Worth running before each deploy.

### Three strings still need your approved copy

They are grouped under `PLACEHOLDER_COPY` at the bottom of `src/lib/copy.ts` and render with a
visible `[—]` marker so they can never be mistaken for final text:

1. **Footer privacy link label** — currently `[—] الخصوصية`.
2. **`/privacy` page title** — currently `[—] الخصوصية`.
3. **`/privacy` page body** — four placeholder lines covering: responses are collected for
   product research; no name, email or phone is requested; anonymous technical information may
   be collected; advertising analytics such as Meta Pixel may be used.

Replace the values, delete the notice block in `src/app/privacy/page.tsx`, and remove the
`robots: { index: false }` override on that page. The `mark()` helper in `copy.ts` adds the
`[—]` prefix — delete it once the copy is approved.

Image alt text (`ALT` in `copy.ts`) is minimal and factual — the brand name plus the approved
colour word. Adjust it if you prefer different wording.

## 9. Analytics

### Meta Pixel

Set `NEXT_PUBLIC_META_PIXEL_ID`. With it empty, no script loads and no requests are made.

| Event | Type | Fires when |
| --- | --- | --- |
| `PageView` | standard | Page load, from the pixel's own base snippet |
| `ViewContent` | standard | Product block is 50% visible for 500ms |
| `FormStart` | custom | First focus inside the questionnaire, once per session |
| `FormSubmit` | custom | **Only after the database confirms the write**, once per session |

`FormSubmit` never fires on a button click. The order is always: write to the database → confirm
→ track → show the success state.

### Internal funnel

Four anonymous events land in `survey_events`, at most once per session each, which makes the
dashboard maths exact:

```
form start rate       = form_start   ÷ page_view
submission rate       = form_submit  ÷ form_start
session → submission  = form_submit  ÷ page_view
```

`form_submit` is written **server-side** by the submit route, so it cannot be forged from the
browser or recorded for a failed write.

### UTM attribution

`?utm_source=instagram&utm_medium=paid_social&utm_campaign=hamon_validation`

Captured on load, kept in `sessionStorage` for the visit so it survives scrolling and form
filling, and attached to the submission. A UTM-free visit works exactly the same and is reported
as `(not set)`. `?variant=` overrides `landing_variant` per visit.

### Anonymous session id

A random id generated per browser tab and stored in `sessionStorage`. It separates one visit
from another and makes accidental duplicates detectable. It is **not** a fingerprint: no device,
canvas, font or IP signal feeds into it, it is not shared across tabs or devices, and it is gone
when the tab closes.

## 10. Duplicate protection

Four layers, none of which blocks a legitimate repeat visit:

1. The submit button is disabled while a request is in flight.
2. An in-flight ref rejects a second submit before React re-renders — a double tap sends one request.
3. Each form instance carries a random `submission_token`, so a retry after a timeout resolves
   to the same row instead of creating a second one.
4. `submission_token` is `UNIQUE` in the database, and the insert is an idempotent upsert. A
   duplicate request returns success without writing anything.

If a submission fails, the visitor's answers stay exactly as they left them and the locked
retry message is shown.

## 12. Security

- The browser has **no** database credentials. Every write goes through a server route.
- RLS is enabled with no policies and grants are revoked — the `anon` role can do nothing.
- Payloads are validated server-side against the live survey configuration: an unknown question,
  an unknown option value or a malformed session id is rejected before the database is touched.
- The database enforces the same option values again through `CHECK` constraints, plus length
  limits on every free-text field.
- API responses are opaque. Database, driver and exception details are logged server-side and
  never returned; visitors only ever see the locked Arabic error message.
- Rate limits: 12 submissions / 10 min, 60 events / min, 8 admin login attempts / 10 min per IP.
  The IP is used as a rate-limit key only — it is never stored.
- The admin password is compared through HMAC digests, so timing reveals nothing about it.
- `/admin` and the CSV export are gated by middleware **and** re-check the session themselves.
- CSV export neutralises leading `=`, `+`, `-`, `@` so spreadsheet apps cannot execute a cell.

## 13. Accessibility & performance notes

- Semantic RTL markup: `<html lang="ar" dir="rtl">`, real `<fieldset>` / `<legend>` groups,
  native radio inputs (arrow-key navigation, correct screen-reader semantics), labelled text
  fields, `role="alert"` on validation and submission errors, focus moved to the first
  unanswered question, focus moved to the success heading.
- Visible focus rings everywhere; all tap targets ≥ 48px tall.
- `prefers-reduced-motion` is respected — the entrance transition's hidden state only exists
  when motion is welcome, so the page is fully readable without JavaScript and with motion off.
- Text inputs are 16px on phones so iOS Safari does not zoom on focus.
- Images are responsive with fixed aspect ratios (no layout shift); the hero is priority-loaded,
  everything else is lazy.
- The font is self-hosted with `display: swap`. Client-side JavaScript is limited to the form,
  two IntersectionObservers and the analytics beacon.

## 14. What is deliberately not here

No About/Story/founder section, testimonials, reviews, ratings, FAQ, blog, customer logos,
social proof, statistics, preorder counts, scarcity, countdowns, newsletter signup, price
question, or any claim about comfort, health, posture, materials, weight, durability, launch
dates or shipping. The product has not been manufactured or tested — so the page says nothing
about how it will perform.

The survey is neutral by design: negative options are kept, worded plainly, styled identically
to positive ones, nothing is preselected, and a high-intent answer gets exactly the same
confirmation as a low-intent one.
